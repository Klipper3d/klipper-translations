# 为 Klipper 做出贡献

感谢您为 Klipper 做出贡献！本文档描述了向 Klipper 贡献更改的流程。

有关报告问题的信息或联系开发人员的详细信息，请参阅[联系页面](Contact.md)。

## 贡献流程概述

对 Klipper 的贡献通常遵循一个高层次的流程：

1. 当提交内容已准备好进行广泛部署时，提交者会创建一个 [GitHub Pull Request](https://github.com/Klipper3d/klipper/pulls)。
2. 当有[审阅者](#reviewers)可以[审阅](#what-to-expect-in-a-review)该提交时，他们将在 GitHub 上将自己分配给该 Pull Request。审阅的目标是查找缺陷，并检查提交是否遵循了文档中指定的指南。
3. 成功审阅后，审阅者将在 GitHub 上“批准审阅”，然后由[维护者](#reviewers)将更改提交到 Klipper 主分支。

在进行功能增强时，请考虑在 [Klipper Discourse](Contact.md) 上发起（或参与）一个话题讨论。论坛上的持续讨论可以提高开发工作的可见性，并可能吸引更多对测试新功能感兴趣的用户。

## 审阅时的预期

对 Klipper 的贡献在合并前会经过审阅。审阅过程的主要目标是检查缺陷，并确保提交内容遵循 Klipper 文档中指定的指南。

我们理解完成一项任务有多种方式；审阅的目的不是讨论“最佳”实现。在可能的情况下，审阅讨论应基于事实和测量数据，这更为可取。

大多数提交都会收到审阅反馈。请准备好接收反馈、提供进一步的细节，并在需要时更新提交内容。

审阅者通常会关注以下几点：

1. 提交内容是否没有缺陷，并且已准备好广泛部署？

   提交者应在提交前测试其更改。审阅者会寻找错误，但通常不会测试提交内容。被接受的提交通常在被接受后的几周内就会部署到数千台打印机上。因此，提交的质量被视为优先事项。

   主 [Klipper3d/klipper](https://github.com/Klipper3d/klipper) GitHub 仓库不接受实验性工作。提交者应在自己的仓库中进行实验、调试和测试。[Klipper Discourse](Contact.md) 服务器是提高新工作知名度并找到有兴趣提供实际反馈的用户的好地方。

   提交必须通过所有[回归测试用例](Debugging.md)。

   当修复代码中的缺陷时，提交者应对该缺陷的根本原因有基本了解，且修复应针对该根本原因。

   代码提交不应包含过多的调试代码、调试选项或运行时调试日志。

   代码提交中的注释应侧重于增强代码维护性。提交不应包含“被注释掉的代码”或描述过去实现的过多注释。不应有过多的“todo”注释。

   文档更新不应声明其为“正在进行的工作”。

2. 提交是否为现实世界中执行实际任务的用户提供了“高影响”的好处？

   审阅者需要至少在自己心中明确“目标用户是谁”、“目标用户规模的大致范围”、“他们将获得的好处”、“如何衡量该好处”以及“这些测量测试的结果”。在大多数情况下，这对提交者和审阅者来说都是显而易见的，审阅过程中通常不会明确说明。

   对主 Klipper 分支的提交应具有值得注意的目标用户群。作为一般“经验法则”，提交应针对至少 100 名真实用户的用户群。

   如果审阅者要求提供有关提交“好处”的详细信息，请不要将其视为批评。理解更改的实际好处是审阅的自然组成部分。

   在讨论好处时，最好讨论“事实和测量数据”。一般来说，审阅者不希望看到诸如“有人可能会发现选项 X 有用”之类的回答，也不希望看到诸如“此提交添加了固件 X 实现的功能”之类的回答。相反，通常更倾向于讨论质量改进的测量方式以及测量结果的详细信息——例如，“在 Acme X1000 打印机上的测试显示，拐角有所改善，如图所示……”，或“在 Foomatic X900 打印机上打印实际物体 X 的时间从 4 小时减少到 3.5 小时”。我们理解此类测试可能需要大量时间和精力。Klipper 一些最显著的功能在合并到主分支前经历了数月的讨论、重做、测试和文档编写。

   所有新模块、配置选项、命令、命令参数和文档都应具有“高影响”。我们不希望给用户带来他们无法合理配置的选项，也不希望给他们带来没有显著好处的选项。

   审阅者可能会要求澄清用户如何配置某个选项——理想的回答应包含配置过程的详细信息——例如，“MegaX500 用户应将选项 X 设置为 99.3，而 Elite100Y 用户应使用……程序校准选项 X”。

   如果某个选项的目的是使代码更具模块化，则优先使用代码常量而非面向用户的配置选项。

   新模块、新选项和新参数不应提供与现有模块类似的功能——如果差异是任意的，则最好使用现有系统或重构现有代码。

3. 提交的版权是否清晰、非随意且兼容？

   新的 C 文件和 Python 文件应有明确的版权声明。请参阅现有文件以了解首选格式。对现有文件进行小修改时，不鼓励声明版权。

   来自第三方来源的代码必须与 Klipper 许可证（GNU GPLv3）兼容。大型第三方代码添加应放入 `lib/` 目录（并遵循 [lib/README](../lib/README) 中描述的格式）。

   提交者必须使用其全名在提交信息中包含[“Signed-off-by”行](#format-of-commit-messages)。这表示提交者同意[开发者原创声明](developer-certificate-of-origin)。

4. 提交是否遵循了 Klipper 文档中指定的指南？

   特别是，代码应遵循 [Code_Overview.md](Code_Overview.md) 中的指南，配置文件应遵循 [Example_Configs.md](Example_Configs.md) 中的指南。

5. Klipper 文档是否已更新以反映新更改？

   至少，参考文档必须随代码进行相应更新：
   * 所有命令和命令参数必须在 [G-Codes.md](G-Codes.md) 中记录。
   * 所有面向用户的模块及其配置参数必须在 [Config_Reference.md](Config_Reference.md) 中记录。
   * 所有导出的“状态变量”必须在 [Status_Reference.md](Status_Reference.md) 中记录。
   * 所有新的“webhooks”及其参数必须在 [API_Server.md](API_Server.md) 中记录。
   * 对命令或配置文件设置所做的任何非向后兼容的更改必须在 [Config_Changes.md](Config_Changes.md) 中记录。

   新文档应添加到 [Overview.md](Overview.md) 中，并添加到网站索引 [docs/_klipper3d/mkdocs.yml](../docs/_klipper3d/mkdocs.yml) 中。

6. 提交是否格式良好，每个提交只解决一个主题，且相互独立？

   提交信息应遵循[首选格式](#format-of-commit-messages)。

   提交不能有合并冲突。对 Klipper 主分支的新添加总是通过“rebase”或“squash and rebase”完成。通常不需要提交者在每次更新 Klipper 主仓库时重新合并其提交。但是，如果存在合并冲突，建议提交者使用 `git rebase` 解决冲突。

   每个提交应解决一个单一的高级别更改。大型更改应拆分为多个独立的提交。每个提交应“自成一体”，以便 `git bisect` 和 `git revert` 等工具能可靠工作。

   空白字符更改不应与功能更改混合。一般来说，除非是所修改代码的既定“所有者”，否则不接受随意的空白字符更改。

Klipper 不实施严格的“编码风格指南”，但对现有代码的修改应遵循该现有代码的高层代码流程、代码缩进风格和格式。对新模块和系统的提交在编码风格上有更大的灵活性，但最好让新代码遵循内部一致的风格，并普遍遵循行业通用的编码规范。

讨论“更好的实现”不是审阅的目标。然而，如果审阅者难以理解提交的实现，他们可能会要求更改以使实现更透明。特别是，如果审阅者无法确信提交没有缺陷，则可能需要进行更改。

作为审阅的一部分，审阅者可能会为某个主题创建一个替代的 Pull Request。这可能是为了避免在次要程序性项目上进行过多的“来回”讨论，从而简化提交流程。也可能是由于讨论激发了审阅者构建替代实现的灵感。这两种情况都是审阅的正常结果，不应被视为对原始提交的批评。

### 协助审阅

我们非常感谢对审阅的帮助！执行审阅无需成为[列出的审阅者](#reviewers)。我们还鼓励 GitHub Pull Request 的提交者审阅他们自己的提交。

要协助审阅，请遵循[审阅时的预期](#what-to-expect-in-a-review)中概述的步骤来验证提交。完成审阅后，在 GitHub Pull Request 中添加一条评论，说明您的发现。如果提交通过审阅，请在评论中明确说明——例如“我根据 CONTRIBUTING 文档中的步骤审阅了此更改，一切看起来都很好”。如果无法完成审阅中的某些步骤，请明确说明已审阅和未审阅的步骤——例如“我没有检查代码中的缺陷，但我审阅了 CONTRIBUTING 文档中的其他所有内容，看起来都很好”。

我们也非常感谢对提交的测试。如果测试了代码，请在 GitHub Pull Request 中添加一条评论，说明您的测试结果——成功或失败。请明确说明已测试代码及结果——例如“我在我的 Acme900Z 打印机上用花瓶打印测试了此代码，结果良好”。

## 提交信息的格式

每个提交应具有类似以下格式的提交信息：

```
模块: 首字母大写、简短（50 个字符或更少）的摘要

更详细的解释性文本（如有必要）。将其换行至大约 75 个字符左右。在某些上下文中，第一行被视为电子邮件的主题，其余文本被视为正文。摘要与正文之间的空行至关重要（除非完全省略正文）；如果将两者连在一起，rebase 等工具可能会感到困惑。

后续段落应放在空行之后。

Signed-off-by: 我的名字 <myemail@example.org>
```

在上述示例中，`模块` 应为仓库中文件或目录的名称（不含文件扩展名）。例如，`clocksync: 修复连接时 pause() 调用中的拼写错误`。在提交信息中指定模块名称的目的是为提交注释提供上下文。

每个提交都必须有“Signed-off-by”行——它证明您同意[开发者原创声明](developer-certificate-of-origin)。它必须包含您的真实姓名（抱歉，不接受假名或匿名贡献）和有效的电子邮件地址。

## 为 Klipper 翻译做贡献

[Klipper-translations 项目](https://github.com/Klipper3d/klipper-translations) 是一个致力于将 Klipper 翻译成不同语言的项目。[Weblate](https://hosted.weblate.org/projects/klipper/) 托管所有用于翻译和审阅的 Gettext 字符串。当满足以下要求时，区域设置可以在 [klipper3d.org](https://www.klipper3d.org) 上显示：

- [ ] 75% 总覆盖率
- [ ] 所有标题（H1）已翻译
- [ ] 在 klipper-translations 中提交了更新的导航层次结构 PR。

为了减少翻译领域特定术语的错误并了解正在进行的翻译，您可以提交一个 PR 来修改 [Klipper-translations 项目](https://github.com/Klipper3d/klipper-translations) 的 `readme.md`。一旦翻译完成，就可以对 Klipper 项目进行相应的修改。

如果 Klipper 仓库中已存在翻译但不再满足上述清单要求，则在一个月内无更新后将被标记为过时。

一旦满足要求，您需要：

1. 更新 klipper-translations 仓库的 [active_translations](https://github.com/Klipper3d/klipper-translations/blob/translations/active_translations)
2. 可选：在 klipper-translations 仓库的 `docs\locals\<lang>` 文件夹中添加一个 manual-index.md 文件，以替换语言特定的 index.md（生成的 index.md 无法正确渲染）。
